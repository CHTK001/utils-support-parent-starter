Key Findings

Analysis
  • JDK most stable at high concurrency: jdk-tcp p50 from 149us (10c) to 159us (1000c) = 1.1x, while vertx-http p50 from 473us to 15,468us = 32x degradation. JDK blocking I/O + virtual threads keep latency nearly constant.
  • Vert.x latency explodes under load: vertx-tcp-proxy p50 760us to 20,885us (27x), http 641us to 28,324us (44x). Event Loop blocked, cannot schedule efficiently.
  • jdk-tcp linear scaling on delay: 10c 5 TPS to 500c 223 TPS (near-linear), SR 95.96%. Virtual thread scheduler excels at blocking operations.
  • Vert.x collapses on delay: vertx-http 500c SR only 65.14%, vertx-tcp-proxy cannot complete 100+ concurrency tests. Event Loop fully blocked by Thread.sleep.
  • TCP proxy best scaling: tcp-proxy TPS stable 17,674-19,105 from 10c-1000c, p50 only 328us to 452us (1.4x). Pure byte forwarding, no framework overhead.
  • HTTP proxy is bottleneck: vertx-http-proxy 1000c p50 reaches 30,450us, SR 97.11%. Short connection + HTTP parsing double overhead.

nio-http Optimization

Optimized
  • Header Map: TreeMap(case-insensitive) → HashMap, key lowercased at feed time, lookup O(log)→O(1).
  • Zero-copy feed: removed byte[] chunk = new byte[toCopy] temp alloc in feed(), now buf.put(data) transfers bytes directly.
  • Empty body constant: resolveBody() returns shared EMPTY_BYTES instead of per-request new byte[0].
  • gather write: writeToChannel() uses channel.write(ByteBuffer[]) gather write, replacing per-buffer loop.
  • inline dispatch: bench.fast=true forces setting.setInlineDispatch(true), event loop thread directly parses+handles+writes echo, skipping virtual-thread submit & selector wakeup. TPS 18k→20k.
  • Result: nio-http inline TPS=20,122 @1000c, matches jdk-tcp pure-TCP ceiling (20,222). p50 stable 217-271us. Echo Raw Data table nio-http rows = inline-mode values.

Proxy Findings

Analysis
  • tcp-proxy (JDK) best: TPS stable 15-19k across all concurrency, p50 316-619us. Byte forwarding, no protocol parsing overhead. 2 backend instances + ServiceDiscovery round-robin, verified both backends receive equal requests.
  • http-proxy (JDK) close second: TPS 16-17k, p50 361-609us. Same byte forwarding model as tcp-proxy (JdkHttpProxyServer extends TcpProxyServer). ~10% slower than tcp-proxy due to backend HTTP parsing overhead.
  • Vert.x proxies collapse under load: vertx-tcp-proxy p50 from 789us (10c) to 32,458us (1000c), vertx-http-proxy p50 from 1,554us to 33,303us. Event Loop saturation at high concurrency.
  • JDK proxy 2-3x faster than Vert.x: tcp-proxy 18,433 vs vertx-tcp-proxy 6,967 @1000c (2.6x). http-proxy 16,324 vs vertx-http-proxy 5,917 @1000c (2.8x).
  • All proxies through ServiceDiscovery.getService(): Full resolution path via ProxyTargetResolver, same as ServiceDiscoveryServerFilter logic. 2 backend round-robin verified.
