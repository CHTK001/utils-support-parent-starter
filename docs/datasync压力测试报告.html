调度时序诊断 · TickDebugProbe

cron=0/1 · 5s
配置：cron=0/1（每秒触发），CSV 1 行，CountSink，5 秒观测窗口
结果：4 次 write（理论 5~6 次），启动瞬间出现同毫秒双写（48.070 + 48.071），其余每秒 1 次正常
结论：稳态频率正常（每秒 1 次），启动首轮存在重复执行 bug（影响：每次启动多一轮全量同步），已知问题记录
触发路径：executorManager.start() → schedulerManager.start(initialDelay=1s) 后，启动链路另有隐式首轮触发

Datalake 远程→本地全链路

5/5 PASS
链路：CSV 源（50行）→ DataSync 调度 → DatalakeExecutorManager → DatalakeReactorExecutor（Map→DataEnvelope）→ PipelineEngine → 4 Sink 同时分发

Bug 修复：DefaultPipelineEngine 原实现查找到 sink 后调用 dispatcher.publish() 而非 target.write()，导致数据进入 Chronicle 但无人消费。已修复为直接调用 sink.write()

已知问题

Known Issues
  • 启动首轮重复写入：DefaultDataSyncServer.start() 调用链中，executorManager 与 schedulerManager 各自触发一次首轮同步， 导致同毫秒双写。已通过 lastExecutionTimeMap 去重修复 scheduler 链路，启动链路（非 scheduler）仍有残留，影响可忽略（每次冷启动多 ~1 批全量同步）。
  • 100M+ OOM：100M 行 ×5 字段 ×~300B/Map ≈ 30GB 瞬时对象，4G 堆上限触发 OutOfMemoryError。 10M 是当前架构可靠上限；100M+ 需流式处理（避免全量 Map 实例化）或列式存储（Arrow/Parquet）。

已知问题与优化方向

Known Issues
  • [P0] 调度启动重复执行：schedulerManager.start() 与 executorManager.start() 触发首轮同步，同一毫秒出现双写。修复方案：区分首次启动与稳态触发。
  • [P0] 100M 压力测试 OOM：100M 行 × 5 字段 ≈ 30GB 瞬时 Map 对象 > 4G 堆。需流式处理（Iterator）或列式存储。
  • [P1] PipelineState 枚举不完整：当前含 FILTERED/PARSED/CLEANED/STANDARDIZED/SINK_OK/SINK_FAIL，缺 TRANSFORMED、VALIDATED 等中间态。
  • [P2] DispatcherProvider 默认使用 Chronicle：可通过配置切换为 InMemory 或 WAL+Jackson。
  • [P2] 主动推送能力待实现：SubscriberManager → AccessSink 的实时推送链路尚未完整打通（目前仅 MockSink + StatisticSink 支持访问模式）。
