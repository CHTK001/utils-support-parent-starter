4结论与建议

✅ 选型结论
  • 小报文 / 中低并发 → NioHttpServer：256B 下四个并发档全部第一（cc100 达 22.4k RPS、p99 仅 21ms），零外部依赖纯 JDK 实现。
  • 大报文 / 高并发 → VertxHttpServer：4096B 从 cc500 起持续反超，cc2000 时 11.3k RPS 为 NIO 的 2.1 倍；高并发下尾延迟也最低（p99 747ms vs NIO 2475ms / JDK 2975ms）——h2c 多路复用 + maxConcurrentStreams≥1024 调优生效。
  • JdkHttpServer 全面第三：低并发尚可（13.9k @4096B/cc100），但 cc2000 时吞吐跌至 2.1k、p99 近 3s，仅适合轻量内嵌场景。
  • 退化拐点：NIO 在 cc500→2000 区间吞吐衰减约 57%（Windows eventLoop 钳制为 2 所致）；Linux/epoll 不受此限，预计高并发段表现会显著更好。
⚠️ 限制说明
  • 环境敏感：共享开发机繁忙期（CPU>80%）所有实现成功率会跌至 17%~50%——其中 HTTP 503 是框架内置 maxConcurrency 限流的主动甩负载（保护行为），另有少量 ConnectException（backlog 瞬时打满）。本报告数据全部在 CPU<35% 空闲窗口采集。
  • Windows 钳制：NIO 的 eventLoop 在 Windows 上被钳制为 2（WindowsSelectorImpl 多 Selector 并发不稳定），Linux/epoll 下按核数扩展。
  • 每场景 ~20000 请求、自适应请求数（ceil(20000/并发)×并发）、预热 200 次；失败请求不计入分位数统计。
