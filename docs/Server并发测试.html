4AIO 功能覆盖：HttpServerExample 22/22 全部通过

✅ AioHttpServer v2 能力实测（--type=aio --mode=func，22 项断言全过）：
  • SSL/TLS：每连接 SSLEngine，握手在专属虚拟线程以 Future 阻塞驱动；数据面 unwrap 内联于 proactor 读回调、wrap 在响应入队时同步完成。修复要点：握手缓冲区写/读模式显式 flip/compact（否则解析到空缓冲垃圾字节）、TLS1.3 server flight 分片续写、禁用 NewSessionTicket 防票据明文污染 HTTP 解析器。
  • WebSocket (RFC 6455)：升级握手后切换帧协议；支持 @OnMessage 注解与 onSubscribe(topic, handler) 订阅、ping/pong、close 回显、publish 广播；TLS 连接下帧收发自动加解密。
  • SSE 流式推送：为 NioServerResponse 新增 streamWriter 直写钩子，SSE 事件经 TLS 感知阻塞写输出（此前 channel=null 被静默丢弃导致 EOF）。
  • 其余 19 项（方法矩阵/状态码/Keep-Alive/大报文/Header 大小写/限流 503/RemoteAddress 等）回归通过。

4.5最新复测：AIO 响应式 + 极限优化（2026-08-24 追加）

AioHttpServer 完成纯非阻塞改造（TLS 握手状态机 / WS 增量解码 / SSE 入队化）后追加：
优化项说明效果
响应式模式非阻塞 handler 内联 IOCP 回调线程执行，消除每请求 2 次虚拟线程调度跳转（setting.setReactor(true) 或 -Daio.http.reactive=true）cc500 小报文 +33%，p50 35ms→29ms；cc2000 首测反超 NIO（10,604 vs 6,343）
头体合并单次写≤64KB 响应合并为单缓冲一次 overlap 写（堆分配，TLAB 近零成本）省一次内核往返；4096B/cc500 历史最佳 14,620
无超时读热路径 read 去掉超时参数（Windows 定时异步读需挂内核等待对象）p50 首次进入个位数稳定区（3~8ms），同窗口始终 ≤ NIO 一半
同窗口 NIO-vs-AIO 复测两轮结论：①较空闲窗口小报文低并发 NIO 快、高并发 AIO 反超；②负载回升窗口 AIO 全档领先且 p50 仅 NIO 一半。两实现峰值已同量级（15~20k 档）；最终排名建议 Linux 独占机复测定案。

6结论与选型建议

✅ 选型结论
  • 综合首选 NioHttpServer：8 档 6 冠、平均吞吐最高（18.5k），纯 JDK 零依赖；小报文低并发（cc100 23.3k）与大报文中高并发均领跑。
  • 持续高并发负载选 AIO：请求吞吐维度上它是唯一随并发单调上升的实现（256B：7.1k→11.0k），且 cc2000 小报文尾延迟全场最低（766ms）；连接规模维度优势更显著——10k 长连接下吞吐达 NIO 的 2 倍（见 §5）。现已具备 SSL/TLS 与 WebSocket 完整能力。
  • 可预期性优先选 Vert.x：各档表现平稳（p99 中高并发段多项最优），综合第二。
  • JdkHttpServer 仅适合突发短促流量：cc100 两度夺冠但 cc1000 起崩塌至 ~2k-5k，长稳场景不推荐。
  • Windows 注意：NIO 的 eventLoop 被钳制为 2（WindowsSelectorImpl 限制），Linux/epoll 下预计更高；AIO 在 Windows 底层为真 IOCP，优势场景恰在此平台。
⚠️ 限制说明
  • 共享开发机存在 run-to-run 方差，绝对值仅供参考；同窗口内四实现的相对排序是本报告结论依据。
  • AIO v2 不支持 ACME 自动证书与客户端证书双向认证；WS 帧循环运行于每连接虚拟线程，海量长连接时注意虚拟线程规模。
