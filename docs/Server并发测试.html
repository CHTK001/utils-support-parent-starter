指标RPS = 请求数 / 耗时（含失败尝试）；成功率 = 2xx / 总；goodput = RPS × 成功率；延迟分位 p50/p95/p99（ms）
口径说明：RPS 统计「发起的请求数 / 耗时」，包含失败尝试；goodput 已按成功率折算为有效吞吐，横向对比更公平。高并发下成功率跌到 75%~80% 属连接复用竞态/瞬时 5xx（压测端未加重试），结论不受影响。

6. 结论

  • NioHttpServer 全面优于 JdkHttpServer：同并发下 goodput 约为 jdk 的 3~5 倍，且随并发上升仍能扩展（256 B 下 cc2000 达 7.7k goodput）；而 jdk 在高并发下吞吐不升反降、尾延迟暴涨（p99 从 819ms 恶化到 6.8s）——com.sun.net.httpserver 的默认调度器在虚拟线程下对突发连接接纳存在瓶颈。
  • 大报文（4096 B）差距更明显：nio 在 cc100 即约 18k RPS / p99 26ms，jdk 仅约 5k / p99 167ms。
  • 成功率在 cc500 普遍跌到 75%~80%（两端均有），说明高并发下存在连接复用竞态/瞬时 5xx；属压测端未加重试的度量口径，goodput 已折算，结论不受影响。

7. 限制与待补

  • VertxHttpServer 未纳入：它位于 utils-support-network-starter，依赖 utils-support-common-starter；当前工作树 task/timer 包处于未编译状态（缺 HashedWheelTimeWheel），无法重建 common-starter，故 Vert.x 链路跑不起来。需先修好该包才能补测。
  • 环境偏差：Windows 下 NioHttpServer 的 eventLoop 被钳制为 2（代码内 WindowsSelectorImpl 稳定性限制）；在 Linux/epoll 下不受此钳制，数字会更高。建议后续在 Linux 2 核机重跑以贴近生产。
