# 远控网关：进度与计划

> 更新时间：2026-09-07 · 版本 4.0.0.42 · 仓库 `utils-support-parent-starter/utils-support-remote-parent`

## 一、总体架构

```
utils-support-remote-parent
├── utils-support-remote-protocol     // 信令/帧/能力模型/SPI（AgentType 三模式、Session.agentType、NegotiatedCodec.targetEncoding）
├── utils-support-remote-core         // 零拷贝传输（FrameServer/FrameClient/FrameCodec 二进制帧、RemoteTransport/RemoteFlow/RemoteServer/Client）
├── utils-support-remote-gateway      // 网关（GatewayServer、AuthManager、SessionManager、RouteManager、TranscodeEngine+GatewayTranscoder）
├── utils-support-remote-agent        // 被控端（三模式：FORWARD 纯转发 / SHELL 套壳自启 freerdp 或自研 / PUSH 纯自研实时推送仅监控）
└── utils-support-remote-controller   // 控制端（ControllerClient、DecoderRenderer、InputInjector；Web 控制端见计划）
```

**Agent 三模式**（用户确认）：
| 模式 | 能力来源 | 说明 |
|---|---|---|
| FORWARD | 三方软件（freerdp/vnc/ssh） | 被控端仅做会话桥接转发 |
| SHELL | 自启 freerdp+转发，或自研 | Java 启动器套壳 |
| PUSH | 纯自研 | 实时画面推送，**仅监控无远程控制**（控制端已实现禁控守卫） |

**编解码协商规则**（用户确认，TranscodeEngine 已实现）：
1. 被控端编码优先：按**被控端**编码列表顺序找与控制端解码能力的交集（如默认 `h264` 优先、`jpeg` 兜底）
2. 交集为空（都不一致）→ **网关转码**：源=被控端第一个编码，目标=控制端第一个支持编码（`transcoded=true`，`GatewayTranscoder.transcode` 兜底执行）
3. 服务端不额外推 JPEG/不做无关转码——一致时帧原样透传

## 二、当前进度（已完成并验证）

### 1. 零拷贝传输层（remote-core）✅
- 二进制定长前缀帧：`totalLen|type|sidLen|metaLen|payloadLen|sessionId|meta(json)|payload`，**无 buffered 流、无 Base64、无字符串中转**
- 写路径 gather（payload `ByteBuffer.wrap` 零复制）；读路径 payload 直读目标 byte[]
- `FrameServer`/`FrameClient`：NIO 阻塞通道 + 虚拟线程一连接一线程；hello 握手（首帧 CTRL+meta{kind:hello, clientId}）注册连接身份，`connect()` 同步等 ack
- `RemoteTransport`/`RemoteFlow` API不变换底座；连接标识=定向路由键（控制端传接入令牌）
- 修复：readBinary 跳长度字段误用 1 字节 → 字段错位、读线程静默死亡（虚拟线程任务须兜底 catch Exception）
- 修复：`FrameServer.closeQuietly(SocketChannel)` 缺失 → 添加静态 helper；`FrameCodec.writeBinary` 参数从 `WritableByteChannel` 改为 `GatheringByteChannel`（`SocketChannel` 实现此接口，支持 `write(ByteBuffer[])` gather 写）

### 2. 控制端 Java 侧（remote-controller）✅
- `ControllerClient`：以接入令牌注册连接、信令上报 ControllerInfo、startSession（预生成 sessionId + Session 信令携带 verifyCode 元数据）、closeSession、sessionEstablished、PUSH 会话拒绝键鼠注入
- `DecoderRenderer`：热路径仅解码一次（1080p 162ms→33ms/帧），`setFrameListener` 交付嵌入方绘制；缩略图由解码结果缩放
- 冒烟 `RemoteCoreControllerSmokeTest` **11/11**（含 256KB 大帧字节级一致）

### 3. 网关与协议 ✅
- 鉴权模型：agentRegister 首次注册登记验证码（重复注册校验一致性）；controllerConnect 令牌即凭据首次接入注册；createSession 校验被控端验证码
- handleSignal 按 kind 元数据分发 AgentInfo/ControllerInfo 注册信令；CTRL 帧按会话→agentId 定向路由
- Session 携带 agentType；NegotiatedCodec 含 encoding/targetEncoding/width/height/quality/transcoded

### 4. 性能基准（RemotePerfBenchmark）
- 编解码：二进制 1015~2577 MB/s vs JSON+Base64 66~79 MB/s（**16~40x**）；线上体积省 ~36%
- 真实 TCP 全双工（300 帧/档全达）：720p 上行 205 MB/s；**1080p 下行 6328fps/396MB/s、上行 6764fps/423MB/s**
- 渲染热路径去 4.9x 浪费；下一个天花板：1080p 解码 33ms（ImageIO）→ 计划换 javacv/ffmpeg

### 5. 全部 6 模块 reactor 编译通过 ✅
- remote-protocol、remote-core、remote-gateway、remote-agent、remote-controller 全部 **BUILD SUCCESS**
- 改动已入库（`git add` + commit）

### 6. 原生采集三平台（remote-agent）✅
- `NativeScreenCapture`：Windows GDI（`CreateCompatibleDC+BitBlt+GetDIBits`）/ **Linux X11**（`XOpenDisplay+XGetImage`——XImage 为 PointerType，`XImageStruct` 按 Xlib 布局 Structure 映射读取字段）/ **macOS CoreGraphics**（`CGDisplayCreateImage`——jna-platform 无 mac 封装，自定义 `CoreGraphics` JNA 直连）——三平台占位符清零
- `NativeFrame` 原始像素帧：采集/编码全程**不经 BufferedImage**（raw 字节显式拷贝）；多屏原始行拼接（`System.arraycopy`）
- 采集性能：逐像素 `setRGB` → raster `DataBufferInt` 直写（约 10x）；GetDIBits 经 `Memory` 显式读写（非零拷贝共享缓冲）
- `ScreenCapture` 包装 `NativeScreenCapture`：`captureFrame()` 返回 `NativeFrame`，`capture()`/`captureBufferedImage()` 仅消费边界转换

### 7. 自研编码 SPI 架构（remote-agent）✅
- `FrameEncoderSpi`（原始帧编码契约——`codecName()/encode(NativeFrame,quality)/close()`）
- `@Spi("jpeg")` `JpegFrameEncoder`：`RawJpegEncoder`（`PixelInterleavedSampleModel` 包装原始字节 + `RawRasterImage`（RenderedImage）→ ImageIO ImageWriter——无 BufferedImage）
- `@Spi("h264")` `H264FrameEncoder`：`NativeVideoCodec`（Rust JNI 原生）——RGB→BGR24 显式转换 → `h264Encode`（句柄生命周期 + 尺寸变更重建）
- `NativeEncoder` 按协商编码名经 `ServiceProvider.of(FrameEncoderSpi.class)` 加载（缓存 + close 传播）；默认编码集 `["h264","jpeg"]`（h264 优先）
- 修复：`RenderedImage.getSources()` JDK25 返回 `Vector`（非 List）；`Gdi32`→`GDI32`（jna-platform 5.12.1 全大写）；`Structure.fromPointer`→`newInstance`；`WinDef.HANDLE`→`WinNT.HANDLE`；`WinGDI.SRCCOPY` 缺失用字面量 `0x00CC0020`

### 8. 网关转码执行（remote-gateway）✅
- `GatewayTranscoder`：H264↔JPEG 双向——JPEG→H264（ImageIO 解码 → BGR24 → 原生 `h264Encode`）；H264→JPEG（原生 `h264DecoderCreate/h264Decode` → RGB → Raster 包装 JPEG——无 BufferedImage 中间态）
- `TranscodeEngine.negotiate` 修复：`needTranscode` 大小写 bug（`"jpeg"≠"JPEG"` 恒 true → 仅交集为空才转码）；空交集时源=被控端编码、目标=控制端解码能力（`NegotiatedCodec.targetEncoding`）
- `GatewayServer.routeData` 钩子：`transcoded=true` 会话的 DATA 帧先 `TranscodeEngine.transcode` 再 `publish`（控制端↔网关交互点的编解码适配）

### 9. 桌面支持上报与门控（remote-agent）✅
- `AgentInfo.desktopSupported` + `AgentBootstrap.detectDesktopSupported()`（Windows/macOS 恒真；Linux 查 `DISPLAY`——无则 headless）
- 桌面门控：PUSH（桌面采集）模式 + `desktopSupported=false` → **拒绝桌面连接、降级到套壳模式**（SSH/RDP/VNC 仍可用）——控制端连接协议：选 SSH 走 SSH；选桌面由 Linux headless 判定拒绝
- `AgentBootstrap.main` 部署入口：`args[0]=网关地址 / [1]=agentId / [2]=verifyCode / [3]=agentType(PUSH/SHELL)`

### 10. 套壳模式完整实现（remote-agent）✅
- **`AgentInfo` 新增字段**：`host`（套壳目标主机）、`port`（目标端口）、`username`、`password`——替代硬编码凭据
- **`SSHTunnelManager` 重写**：
  - `createRDPTunnel`/`createVNCTunnel`/`createSSHTunnel`：先创建 SSH 隧道（`SshClient.builder` + `SshTunnel`），再启动对应客户端
  - `startFreerdp`：通过 `127.0.0.1:rdpLocalPort` 连接（SSH 隧道转发后的本地端口）
  - `startVncViewer`：通过 `127.0.0.1:vncLocalPort` 连接
  - `startSshShellViaClient`：用 `SshClient.terminal()` 启动 PTY 交互式终端
  - `startSshShell`：通过 SSH 隧道启动 `ssh` 命令行
  - `closeAll`：按类型关闭所有隧道和客户端
- **`AgentShellService` 重写**：
  - `determineShellMode()`：根据 `platform` 判断 RDP/VNC/SSH
  - `startRDPSession()`：从 `AgentInfo` 读取 `host/port/username/password`，创建 SSH 隧道 + 启动 freerdp
  - `startVNCSession()`：同流程，创建 VNC 隧道 + 启动 vncviewer
  - `startSSHSession()`：创建 SSH 隧道 + 启动 PTY 终端
  - **`TelnetServer` 集成**：套壳模式启动时自动启动 4567 端口 Telnet Shell（APM 监控、状态查看）
- **依赖**：`utils-support-runtime-shell`（TelnetServer/ShellSession/Telnet 命令系统）
